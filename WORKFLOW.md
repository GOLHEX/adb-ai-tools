# Рабочий цикл: от страницы портфеля до применённых метаданных

Один проход = одна пятёрка страниц портфеля (500 работ). Всё, кроме написания метаданных,
делает скрипт `04_automation/adobe_edit.js`.

## Порядок команд

```
1_start_chrome.bat                  Chrome с отладочным портом, залогиниться, открыть портфель
node adobe_edit.js --harvest 18 22  выгрузить 5 страниц: данные + превью 500px
node adobe_edit.js --sheets         собрать 25 контактных листов по 20 работ
```

Дальше листы уходят на разбор, оттуда возвращается `03_metadata/pNN_blockN.csv`
с колонками `media_id,title,keywords,category`, и:

```
node adobe_edit.js --apply ..\03_metadata\pNN_blockN.csv --dry   проверка
node adobe_edit.js --apply ..\03_metadata\pNN_blockN.csv         боевой прогон
```

## Три защиты, которые нельзя отключать

| защита | файл | что делает |
|---|---|---|
| проданные работы | `02_data/assets_lifetime_2y.csv` | работа, продавшаяся хотя бы раз, не правится никогда |
| уже отредактированные | `04_automation/edited_log.csv` | повторная правка пропускается |
| сухой прогон | ключ `--dry` | показывает тело запроса, ничего не отправляет |

Обход есть только явный: `--no-skip-sold` и `--redo`. Обе пишут предупреждение в лог.

Почему проданные не трогаем: работа уже нашла покупателя и заняла позицию в выдаче.
Правка метаданных сбрасывает накопленные сигналы ради гипотезы. Риск больше выгоды.

## Размер блока

40 работ на блок. Меньше — растёт доля накладных расходов, больше — тяжело удержать
качество заголовков. Один контактный лист = 20 работ, то есть блок это два листа.

Пауза между работами при отправке — 3 секунды. Ускорять нет смысла: узкое место
не в скорости запросов, а в написании метаданных.

## Что накапливается по ходу

| файл | что в нём |
|---|---|
| `04_automation/portfolio_dump.csv` | id, uuid, категория, имя файла, старые title и keywords |
| `04_automation/edited_log.csv` | что и когда отредактировано |
| `04_automation/apply_report.json` | ответы сервера последнего прогона |
| `05_previews/<id>.jpg` | превью 500px, качаются один раз |
| `05_previews/sheets/` | контактные листы |
| `06_knowledge/themes_registry.csv` | media_id → тема (дописывается после каждого блока) |
| `06_knowledge/THEMES.md` | сводка по темам и их отдаче |

## Правило после каждого блока

Дописать `themes_registry.csv` и пересобрать таблицу в `THEMES.md`.
Без этого разбор превращается в механическую правку и не даёт ответа на главный вопрос —
**из чего вообще состоит портфель и что из этого продаётся**.

## Главное правило по направлениям работы

У нас два направления, и они не равны по приоритету:

1. **Редактирование уже существующих работ в портфеле** — это текущая работа.
   Мы берём реальные files, которые уже есть в Adobe, и правим их под buyer intent и нишевую разгрузку.
2. **Описание новых работ для будущей загрузки** — это вторичное направление.
   Его нельзя использовать как альтернативу текущей правке; оно служит только подготовкой к следующему циклу.

В данный момент мы не “генерируем идеи” ради объёма. Мы действуем по факту наличия работ в портфеле,
потому что от этого зависит и скорость, и качество обратной связи.

Главный принцип: не превращать один и тот же визуальный мотив в десятки конкурирующих работ в одной теме.
Нужно распределять варианты по разным commercial intents и нишам, чтобы не мешать друг другу в выдаче.
